# Recovery and normal-session integration — continuation07

This supersedes the earlier protocol document's engineering status, not its initial-TOFU warning. No independent protocol approval, OTA release, device access or physical acceptance is implied.

## Non-destructive recovery

Explicit native `bluetooth/remote_recover {id,confirmed:true}` selects an EXISTING persisted binding. A 30-second shared-host setup scan/select plus Tag triple press and the existing rapid-blue/quiet-window/short-confirm UX reconnects only that root. No new physical gesture and no silent reenrollment. Published bindings include prepared/commit_pending/active phases, so pending capacity is not invisible. Local WARP Forget is explicitly local and warns it does not reset the Tag.

Recovery type10 hello96: binding id32, fresh CSPRNG challenge32, role1, local durable phase1, reserved30 zero. Both sides reject wrong id/role, absent/invalid phase, zero challenge and nonzero reserved bytes. Fresh root-HKDF salt is the ordered full192-byte WARP/Tag hello transcript; info `WARP recovery proofs v1`. Recovery proofs use distinct CCM domain0x52, version2 AAD and one expected role/kind per stage. Type11..16 carry kinds0..5, each17 bytes. Hello kind0 gates physical confirmation against the new exact transcript, not merely the advertising address.

Kind1 physically confirms Tag -> WARP readback/commit-pending -> kind2 -> Tag readback/commit-pending -> kind3 -> WARP confirms verified mutual durable state kind4 -> Tag verified activation + kind5 final receipt -> WARP verified activation. Active peers revalidate their existing record and do not roll phase backward. Prepared/committing records never authorize operational traffic or become active simply because they survived reboot. Last receipt loss is still a distributed asymmetry; both surviving records can repeat a fresh authenticated recovery without root replacement.

Actual production peer test records the real initial enrollment writes at each phase, then launches fresh processes with independently chosen WARP/Tag saved records. All9 phase combinations run through TeslaVehicle API, shared NimBLE and real Tag GATT/secure/settings, not protocol mocks. These are offline simulated process resets/storage boundaries, not physical power-cut acceptance.

A missing counterpart record cannot be recovered from a BLE address. Orphan Tag owner reset/forget UX is still a decision: no long-hold or extra click gesture has been invented, and the reserved tracking and release-to-submit controls remain unchanged. Ordinary local WARP Forget already requires individual confirmation and never deletes owner-phone/tracker keys.

## Operational admission and wire

Only an active Tag record can open a normal10-second request window from first-short mode fetch or deliberate-shake car-status fetch. Normal advertising uses the distinct request hint UUID suffix0x14; setup/recovery uses0x11. Neither hint authenticates anything. WARP bounded3-second passive normal scans filter0x14 ONLY and explicit setup scans filter0x11 ONLY. Background reception requires remote enabled, at least one active saved binding, radio ready/idle and no Tesla conflict. No second host or Tesla preemption. Scans and exchanges retain the prior cancellation/main/host callback-drain barrier. No pairing click can issue a normal command.

The same RemoteBlinkClient lease sends selection4 for normal sessions, selection1 for enrollment/recovery. Tag accepts4 only in a locally requested normal window. It sends its bound hello; WARP looks up exact binding id within the four-slot active collection. Pending, unknown or wrong peer records fail. The lookup hint remains untrusted until mutual proof.

Type17 hello96: shared binding id32, fresh random challenge32, durable local sequence8 big-endian, role1, reserved23 zero. Both sides reserve AND verify durable readback BEFORE publishing their hello/counter. Keys are root-HKDF64 over the full ordered192-byte hellos and info `WARP operational directional keys v1`: first32 WARP->Tag, next32 Tag->WARP. Root/intermediate buffers are erased after derivation. Domains are distinct from recovery and enrollment; proof/request/response nonces bind0x53,direction,kind with version3/direction/kind AAD. Fixed per-kind nonce is safe only because the full two-random-challenge/counter transcript derives a new directional key each session; retries resend cached identical ciphertext, never a second plaintext under the same key/nonce.

Normal sequence: Tag hello -> WARP hello -> Tag proof kind1/type18 -> WARP proof kind2/type19 -> Tag request kind3/type20 (16 plaintext+16tag) -> WARP reply kind4/type21 (64 plaintext+16tag) -> Tag final receipt kind5/type22. Request contains opcode plus the reserved Tag sequence as transaction id and reserved zero bytes. Exactly correlated16-byte echo is mandatory before Tag accepts a reply. This currently permits only read-only mode/status/harmless diagnostic opcodes1..3, never a charging opcode. Duplicate complete frames trigger only exact cached response retransmission, not another responder invocation/result delivery. Corrupt/interleaved/oversize/out-of-order frames fail closed. Absolute timeout10s, retry500ms; main callback epoch prevents stale-link reuse.

## Real source gate, not fabricated status

Mode request1 now reads the actual `EvseCommon::ManagerModeObservation` populated by the existing manager callback, NOT `evse/charge_mode` requested Config. Only enabled, <=5-second, nonfuture explicit Off/PV/Fast manager modes map to display values. Default/MinPV/other modes are unavailable rather than relabelled. Reply includes valid flag, mode, source age and native-CM/LAN origin1. Tag adds the entire local request elapsed time conservatively before accepting freshness and rejects clock underflow. Host tests inject only the manager boundary and test stale/future/disabled/unsupported modes; the actual source adapter and encrypted return/Tag decode run unchanged.

This is read-only actual manager-echo evidence, not a new charge command ACK and not cryptographically attested evcc ingress: the existing CM LAN transport remains its original trust boundary. No evcc/current-slot writer has been added. Charging control still requires an idempotent authenticated command transaction, one native requested-mode path, supported-mode/authorization/identity gates and a NEW fresh matching manager commit revision after request, never Config equality.

The production session responder now supports a bounded asynchronous finish AFTER request AEAD authentication. Admission runs once; duplicates during the wait do not repeat it. The exact immutable request is retained for correlation, and no provisional reply is sealed. Main-task finish may wait, succeed with a correlated final reply or fail. Pending cancellation/overall10s expiry aborts once and erases session material; it cannot undo a future externally applied write. Actual WARP integration uses this only for read-only mode availability: if no fresh observation exists, wait up to1s for a NEW manager revision, otherwise return authenticated unavailable. An observation arriving at/after the read-wait deadline cannot become late success. Fresh initial mode still returns immediately. Full-GATT tests cover arrival while pending, disable/cancel/drain and exact-deadline late arrival; core tests cover duplicates, expiry, repeated cancel and corrupt final correlation. This asynchronous path is a prerequisite for, NOT an implementation of, the outstanding durable evcc command transaction.

Request2 now carries independent fresh SoC/power observations. Actual accepted authenticated+correlated Tesla results feed a generation/index/MAC-bound observation using ORIGINAL event receive uptime, never response-send time or requested Config. It expires after5s; future time, EV switch, invalid/nonfinite SoC and absent origin reject. EVSE measured input watts comes from the existing assigned charger meter, with its ORIGINAL complete-update timestamp (`finish_update`), checked for future/stale/nonfinite/negative values. This is EVSE input power, not a claim of battery-side power or cryptographic meter attestation. No Tesla poll/wake is added.

Reply bytes23=SoC valid,24=percent,25..28=source age milliseconds;29=power valid,30..33=watts,34..37=power source age, all integers big-endian. The same correlated authenticated ciphertext protects these fields. Tag independently adds conservative entire request elapsed time and stores each valid observation. Remaining zero bytes do NOT imply a rating: max_watts remains0 and combined status display deliberately stays unavailable until verified maximum-rating/phase evidence. Do not call the partial fresh-data transport a completed shake LED feature. ## Native mode preflight — continuation11

`EvseCommon::get_remote_mode_capabilities` is a read-only main-task source, not a writer or authorization token. It requires initialized backend, management enabled, a plugged/non-error charger, successful USER-slot read and no active zero-current user lock, plus fresh/nonfuture manager observation AFTER the hardware read. It intersects the manager's actual supported modes with Off/PV/Fast. Other/default modes are not relabelled. Central-user-management being enabled currently returns unavailable: LED Ack/Nag/Nack feedback is not evidence of a persistent authorization grant, and this adapter does not invent one.

Authenticated mode reply bytes40=Off/PV/Fast bitmask1/2/4 and41=nonzero mask valid. The WARP adapter additionally checks active EV index/MAC against its configured profile and rechecks the live generation after taking the snapshot; mismatch/race clears capabilities without hiding a truthful current charging-mode observation. Tag accepts these fields only with the existing fresh authenticated mode result. A known unsupported further-short selection gets the existing bounded unavailable pattern, never an action. Missing capability evidence preserves the existing selection UI but grants NOTHING; actual submit still unavailable and charging opcodes still rejected. A future writer must revalidate the native gate and active EV at action time, not trust this cached snapshot.

Tests execute the exact native preflight body with only config/hardware/time boundary shims and real generated charge-mode enum. They cover partial/unsupported lists, local lock/read errors, central authorization unknown, initialization/management/plug/error state, stale/future and a slow hardware read. Full actual peer cases prove valid encrypted capability delivery, wrong profile, identity-generation race, and known unsupported selection rejection, all with zero charge calls. Real ELF qualification also requires the native preflight symbol and the Tag capability cache to survive linking.

## Durable operation correlation — continuation10

The actual WARP and Tag now use a shared versioned 180-byte `RemoteOperationJournal` with separately verified readback. WARP NVS namespace/key is `warp_remote`/`operations_v1` (four peer slots); Tag uses only `warp_remote/operation_v1` (one peer slot). Existing 77-byte Tag binding, phone/tracker settings, keys and high-water records are not migrated or overwritten. Journal metadata contains peer identifier, operation ID, opcode, phase and outcome, never roots/private keys or car telemetry. Boot only reads it. A journal fault gates this operation path, not tracking, phone security or read-only mode/status.

The journal is currently integrated ONLY with authenticated harmless diagnostic opcode3, not charging. New operation IDs consume a verified Tag counter reservation before intent is saved; a separate fresh session reserves another counter and may retransmit the same saved diagnostic ID. Only opcode3 permits request bytes1..8 to be a stable nonzero operation ID no greater than the fresh Tag session counter. Mode/status opcodes1/2 still require exact session-counter correlation. Charging opcodes4..6 remain rejected at both transport and Tag entry points; physical submit still indicates unavailable.

Phases1=intent,2=issued,3=final. Every transition writes and verifies readback. WARP performs at most one harmless diagnostic for a NEW record, then persists final outcome before responding. A fresh process loading existing phase1/2 returns UNKNOWN without reissuing or writing the journal. Existing final diagnostic result may be returned without reexecution; it is historical metadata, NOT fresh applied-mode evidence. ID regression, same-ID/different-opcode, overflow/future IDs, pending overwrite and capacity overflow reject. Only confirmed WARP Forget after verified credential removal may retire that peer's journal entry; active peer history cannot be cleared to force retry. Tag owner/phone/tracker records are unaffected.

Diagnostic response byte38=journal result valid;39=0 UNKNOWN,1 harmless DONE,2 REJECTED. Tag verifies/persists its final record before accepting a result. New session `accepted` gate prevents the final authenticated receipt if local commit/readback fails. These flags NEVER drive paired/green or an applied charging ACK.

Full actual-peer tests cut after WARP's final journal commit before Tag receives the complete result, then restart both processes with exact binding/journal records. The same operation ID succeeds without another WARP journal write (Tag session counter3, WARP counter2). Separate cuts after durable WARP intent/issued writes but before readback return restore as UNKNOWN, preserve pending phase and produce zero reissue writes. Tag final-write failure and WARP intent-write failure yield no final receipt/success while the binding stays active. Existing diagnostics use genuine production peer/storage wrappers; the diagnostic trigger and storage faults are host-fixture boundaries. No actual evcc command is executed or claimed.

Outstanding before charging: extend stable intent/payload and retries to real submit, bind it to active EV/authorization/supported modes, persist issue before one native requested-mode action, asynchronously require fresh NEW actual manager commit, persist/read back that result and keep unknown outcomes fail-closed across restart. Do not treat DONE above as that missing applied-state transaction.
